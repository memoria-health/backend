# Soak — sensor/account-room migration

Validates `feat/camera-ownership` (backend), `feat/bridge-core-vendor-split`
(bridge) and `feat/detector-polish` (iOS) against real hardware.

**Automate the checking, not the watching.** `scripts/soak_check.py` asserts
every invariant this migration introduced and exits non-zero on failure:

```bash
watch -n 60 '.venv/bin/python scripts/soak_check.py'
```

`SKIP` is not a pass — it means that check's precondition does not exist yet
(no shared sensor, no identity node) and it has not run.

**3. Nothing is pushed.** `pod.sh deploy` was removed on 2026-08-11 — the node

`pod.sh release`. The dev-code overlay (`scripts/push_node_code.sh`) exists
for iteration and is what a soak should use, but it needs the volume-reader
pod's SSH endpoint, which is not in `.pod.env`.

## Phase 1 — the single Tapo, single patient

The Tapo runs through `nemara-gateway` on the mini-PC. It is the **old**
transport and its single-patient attribution is fine; what is under test here
is that the account-room change did not break the path that already worked.

`Aryaman Bedroom` currently reads `online=false` with `desired_state=connected`
— publishing intent with nothing arriving. Start the gateway and re-run the
checker.

**What to watch, and why it is the interesting bit:** the gateway re-reads
`livekit_room` from the roster on every poll, so it should follow the sensor
from `patient_<id>` to `account_<caregiver_id>` **with no gateway change and no
restart**. If it does, the "publishers that re-read their room can be migrated
underneath them" claim holds. If `online` stays false, that claim is wrong and
everything downstream of it is suspect.

| Check | Passes when |
|---|---|
| `fleet: Aryaman Bedroom online` | frames are landing and the backend can see them |
| `identity: every live sensor has a slot` | the reshard hands this sensor a port |
| `identity: <node> serving` | that port actually answers `/state` — the half that lied in production |

Then, in the app: the sensor appears, the live tile plays, and
`PATCH /v1/cameras/{id}` with `audio_capture_enabled=false` **persists** (it
silently did not until yesterday).

## Phase 2 — add the Warner bridge sensor and a second patient

Different room, different wifi, same account. This is the configuration none
of the code had ever run in.

Order matters: **provision the sensor before adding the second patient.** That
exercises the unassigned-and-streaming state, which is the whole point of the
migration and did not previously exist.

1. Provision the Warner camera through the bridge admin page (see *Manual*).
2. **Before assigning anyone**, confirm it is streaming: `soak_check` shows it
   online, and the caregiver app lists it as unassigned. This is the installer's
   flow — the person on the wall should see it work before leaving.
3. Add the second patient.
4. Assign the Warner sensor to patient 2 only. The stream must not pause.
5. Assign the **Tapo** to both patients. Now one sensor is shared, which is
   what turns on the attribution rules.

**Expected:** `coverage: a shared sensor exists` flips from SKIP to PASS, and
`fleet: a bridge is enrolled multi-tenant` flips from SKIP to PASS — the second
proves the bridge declared `service_kind` and is scoped by `gateway_id` rather
than rebinding the whole service to the last customer.

## What each change is actually being tested by

| Change | Observable |
|---|---|
| Account rooms | Tapo follows its room with no gateway restart |
| Unassigned sensors stream | Warner publishes before any patient exists |
| No primary patient | assigning 2 patients does not move the stream |
| Audio kill on the sensor | PATCH persists and reaches the publisher in ~0.4s |
| Sensor survives patient delete | delete patient 2; the shared sensor stays |
| Identity per sensor | 2 sensors → 2 ports, both answering `/state` |
| `PatientPresence` per patient | patient 1 confirmed on Tapo does not suppress patient 2's detectors on Warner |
| Per-patient attribution | see the detection matrix below |
| Bridge multi-tenancy | provisioning for a second account does not drop the first |
| `worker.py` room shapes | restart the backend mid-soak; both sensors come back online |

That backend-restart test is worth doing deliberately. Until yesterday a
restart spawned no worker for an account room and then swept every bridge
sensor to `online=false`.

## Detection scenarios

Ordinary detectors (fall, wandering, medication) are already exercised. The two
categories never fully tested are **sleep** and **care/behaviour** — both are
`subject_scope="patient"` and non-safety, which is exactly the class the
attribution gate suppresses when identity cannot name who is in frame. They
are therefore the scenarios that prove the rules rather than merely running.

**Sleep** — needs a bedroom sensor and a night. It is a *sustained* detector,
so it exercises episode dedup, which reads `analyses.patient_id`. On a shared
sensor with the second patient, episode boundaries were previously never found,
which re-fired the event every tick. Watch for one sleep event per episode, not
one per tick.

**Care / behaviour** — non-safety and patient-scoped. On the shared Tapo:

| Scenario | Expected |
|---|---|
| Patient 1 alone in frame, identity confirms | event on patient 1 only |
| Patient 2 alone in frame, identity confirms | event on patient 2 only |
| Both in frame | each detector fires for the person identity located |
| Nobody identifiable (back to camera, dark) | **no** care/behaviour event for either |
| Same, but a **safety** detector fires | event for **both** patients |

The last two rows are the agreed rule. A fall nobody can attribute is still a
fall; a care record filed against the wrong resident is not recoverable.

**Identity off** (stop the node): safety and non-safety both keep firing for a
single-patient sensor — the gate only arms where coverage is greater than one.
Worth confirming, because a gate that suppressed everything when the node is
down would take detection with it.

## Manual steps — flag for production automation

| Step | Why manual now | Automation |
|---|---|---|
| **Warner provisioning**: open the bridge page, sign into Warner in the embedded SDK, click `getDeviceList`, pick the camera, type the caregiver email | The vendor's device list is only reachable from their JS SDK in a browser | The real gap. An installer signs into a **vendor** account per install. Worth deciding whether we hold one Warner account for all customers or drive the SDK headlessly |
| **Caregiver email typed by the installer** | It is how the sensor finds the account | Replace with a pairing code — `create_pairing_code` already does this for the wall phone. Today, anyone who knows a customer's email can bind a token and poll their roster (metadata, not video) |
| **Node code deploy** | `pod.sh deploy` removed; needs the reader pod's SSH endpoint, which is not in `.pod.env` | Put `READER_HOST`/`READER_PORT` in `.pod.env.example` and have `push_node_code.sh` read them, so it takes no positional args |
| **`.pod.env` endpoint goes stale on every stop** | RunPod reassigns it | `pod.sh up` already rediscovers. The gap is that `push_node_code.sh` does not use it |
| **Second wifi network** | Physical | none needed |
| **Tapo gateway on the mini-PC** | Deployed hardware | already a systemd unit |

## Aborting

Nothing here writes to production. The deltas are dev-only and each carries a
rollback note. If the soak has to stop, `desired_state='disconnected'` on both
sensors halts publishing without deleting anything, and the sensors keep their
coverage and their identity slots for the next run.
